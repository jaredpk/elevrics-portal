Elevrics Internal

Admin Shell

Cross-tenant console for the client portal. This page is a skeleton — it is not wired to any data source, and no clients are provisioned. It exists so the client tier has somewhere to land when the first engagement is real.

Tenants

No tenants provisioned

Each client will be served at {client}.elevrics.ai by a single host-aware app, with its own Postgres schema. Provisioning a tenant should stay a database write — that depends on wildcard DNS, a wildcard certificate and a wildcard Access policy being configured before the first client is onboarded.

Before the first client

  1. 1 Wildcard DNS + certificate. One *.elevrics.ai record and the Universal SSL wildcard. Never issue per-client certificates — those are published individually to Certificate Transparency logs and would expose the client roster.
  2. 2 Wildcard Access policy. One Access application covering *.elevrics.ai, scoped per tenant by email domain, so onboarding never requires touching Cloudflare configuration.
  3. 3 Tenant model. Organizations, memberships, roles. Postgres schema-per-tenant; isolation enforced at the data-access layer, never left to individual route handlers.
  4. 4 Host/session cross-check. Reject any request where the tenant implied by the hostname disagrees with the tenant in the session claims. This is the backstop against a missing query filter.
  5. 5 Audit logging. Who viewed which tenant's data, and when. Required by the first law-firm security questionnaire, and it is the product Elevrics sells.

Note on placement

This console should move before it holds real client data

It currently shares an origin with the internal modules, which means an XSS in any of them could reach an admin session. That is acceptable while the console is inert. Once it can read client data, split it to its own origin at admin.elevrics.ai — the markup and styles carry over unchanged.
